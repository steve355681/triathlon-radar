# 模型調度守則

> 讀者是未來的主對話模型（可能是 Sonnet / Opus / Haiku）。所有規則在 Sonnet 等級就能執行。
> 事實性內容（模型名、參數）以 2026-07-05 實測為準；若工具 schema 已改變，以現場 schema 為準並依 `04-maintenance.md` 更新本檔。

## 0. 本環境的實際能力（先讀，不要憑印象）

- **可用 agent 類型**（Agent 工具的 `subagent_type`）：`general-purpose`（全工具）、`Explore`（唯讀搜索）、`Plan`（規劃）、`claude`（全工具、預設）、`claude-code-guide`（查 Claude Code/API 文件）、`statusline-setup`（僅狀態列設定，與本 repo 無關）。
- **可指定模型**（`model` 參數）：`haiku`、`sonnet`、`opus`、`fable`。若指定 `fable` 回傳錯誤（方案不支援），改用 `opus` 重派一次。
- **沒有 per-call effort 參數。** Agent 工具無法在呼叫時指定 reasoning effort；effort 只能寫在 agent 定義檔（repo 的 `.claude/agents/<名字>.md` frontmatter——此目錄目前不存在，需要時自行建立）。日常不需要動這個——用模型等級（haiku/sonnet/opus）當成本粗調就夠了。
- **subagent 的工具清單與主對話不同**：例如 `AskUserQuestion` 只有主對話有。派工 prompt 不要假設 subagent 擁有你有的工具；subagent 也不該直接問使用者（問題寫進回報）。
- **成本警告（harness 明文）**：每次 spawn 都是冷啟動，subagent 要重新讀取所有它需要的上下文，在這個方案上是昂貴路徑。所以本守則不是「一律派」，而是「達到門檻才派」。
- **續用比重派便宜**：已跑過的 agent 保有它的 context。同一件事要追問或補做，用 `SendMessage` 傳給原 agent（用它的 ID 或名字），不要開新的。

## 1. 何時派、何時自己做（門檻表）

主對話（指揮官）的職責是決策與整合，不是搬運資料。但在本 harness，spawn 有固定成本，所以：

**自己做（留在主對話）**，當任務是：
- 讀寫少數幾個已知檔案（≤ 5 檔或 ≤ 1500 行閱讀量）。
- 一兩次精準的 `Grep` / `Glob` 就能回答的搜索。
- 本 repo 的日常更新（`index.html` 改資料）——這個 repo 就一個檔案，派工反而更貴。

**派 subagent**，當任務符合任一條：
- 需要通讀 > 5 個檔案或 > 1500 行才能回答（用 `Explore`）。
- 需要抓取多個網頁、且原文不需要進主對話（用 `general-purpose`，結果落檔）。
- **fresh-context 驗證**：重大交付完成後的驗收（見 §5）。這一項不受成本考量豁免——驗收永遠值得派。
- 使用者明確要求用 subagent。
- 多條彼此獨立的工作線可以並行（一次 spawn 多個，同一則回覆內發出）。

**判斷不了就自己做。** 派錯的成本（冷啟動＋來回溝通）通常高於自己做的成本。

## 2. 模型選擇

| 模型 | 用途 | 例子 |
|---|---|---|
| `haiku` | 機械性、判準明確、單步任務 | 「在這 8 個檔案裡找出所有含 `stat-card` 的行號」 |
| `sonnet` | 預設工作馬：搜索、實作、研究、初審 | 「照這個 JSON schema 更新影片卡片並驗證 render」 |
| `opus` | 高風險判斷、二次意見、sonnet 連錯後的接手 | 「這兩種重構方案哪個對弱模型更安全，給理由」 |
| `fable` | 品味與模糊判斷的仲裁（若可用） | 「這三版儀表板文案哪版最好，只回編號與一句理由」 |

## 3. 派工三件套（每個委派 prompt 必含）

1. **目標與動機**：要做什麼、為什麼要做、成品給誰用。subagent 看不到主對話，動機沒寫等於沒有。
2. **驗收條件**：可機械檢查的完成判準（檔案存在、測試通過、回答涵蓋 X/Y/Z）。
3. **回報格式**：明確規定回什麼、多長。

現成模板見 `03-prompt-templates.md`，不要即興發揮。

## 4. 回報合約（寫進每個委派 prompt 的固定段落）

```
回報規則：
- 只回結論與根據，引用一律用 檔案路徑:行號。
- 不要貼大段原文或完整檔案內容。
- 超過 30 行的產出寫到 <指定路徑>，回報中只給路徑與 5 行內摘要。
- 沒找到、做不到、不確定，直說，不要編。
```

主對話收到回報後：只把結論整合進工作，不要求 subagent 重述細節（要細節就 `SendMessage` 問特定一點）。

## 5. 驗證不自驗

寫的人不驗自己的產出。重大交付（新功能、重構、對外文件）完成後：

- **檔案類**：派 fresh-context agent 做 read-back——讀實際檔案，對照驗收條件逐條回答「有/沒有/部分」，並引用行號。
- **程式類**：能跑就實跑（本 repo：用瀏覽器或 node 驗 HTML/JS 至少無語法錯誤、關鍵元素存在）；不能跑才退回 read-back。
- **高風險判斷類**（要不要重構、方案取捨）：找第二意見——派一個 `opus`（或 `fable`）agent，只給它問題與現場材料、不給你的傾向，比對它的結論與你的。或者產出 2–3 個候選答案，派一個評審 agent 選優。

驗證 agent 的 prompt 裡**不要透露「這是我寫的」或你期望的答案**，避免迎合。

## 6. 升降級路徑

- **haiku 錯一次** → 直接升 `sonnet` 重做，不要跟 haiku 來回。
- **sonnet 在同一子任務連錯兩次** → 升 `opus`，並附上完整失敗軌跡（兩次的 prompt、輸出、哪裡錯）。不附軌跡的升級等於重新踩一遍。
- **opus 也解不了** → 停下來回報使用者，附三段：試過什麼、卡在哪、你建議的下一步。
- **解出模式後降級**：一旦某類子任務的解法變成明確步驟（例如「照這個 diff 模式改 10 個地方」），降回 `haiku`/`sonnet` 批次套用，並把模式寫進 `.claude/memory/LESSONS.md`。
- **重試上限**：同一件事、同一種做法最多兩輪。第三次之前必須換做法或換模型或問使用者——連續同法重試是方向錯誤的訊號（見 `02-judgment.md` §4）。
