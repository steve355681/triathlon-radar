# 判斷力外化：rubric 與 checklist

> 這份檔把「強模型憑感覺做對的事」翻成弱模型可逐條核對的判準。
> 用法：遇到標題描述的情境時，逐條走 checklist，不要憑感覺跳過。
> 每條判準附一個正例（✅ 該這樣）和一個反例（❌ 不該這樣）。

## §1 何時該升級模型

升級（換更強的模型重做，路徑見 `01-delegation.md` §6）的觸發條件，符合任一即升：

1. **同一子任務用同一做法失敗兩次。**（此門檻適用 sonnet 及以上；**haiku 例外：錯一次就升**，見 `01-delegation.md` §6——跟 haiku 來回不划算。）
   - ✅ 正例：sonnet 兩次都改錯 `index.html` 的卡片（Edit 錨點撞到別張卡）→ 帶著兩次失敗的 old_string 與錯誤訊息升 opus。
   - ❌ 反例：第一次 Edit 因錨點不唯一失敗，就升級模型。這是錨點問題不是能力問題——先把錨點加長再試一次。
2. **任務需要在多個彼此衝突的目標間取捨，而且沒有現成規則可查。**
   - ✅ 正例：「重構 index.html 會讓每週更新變便宜，但會改變使用者看到的載入行為」——取捨題，派 opus 給第二意見或直接問使用者。
   - ❌ 反例：「JSON 欄位叫 `title` 還是 `name`」——查現有資料照舊即可，不是取捨題。
3. **你發現自己在猜使用者的意圖，而猜錯就要重做的部分，超過你目前已完成的部分。**（可量化代理：重做量 > 已完成量 → 升級或問人；反之先做完再確認。）

**不升級**的情況：缺的是資訊而不是智力（先去查）；錯誤來自工具用法（先讀工具說明）；任務本來就該問使用者（見 §3）。

## §2 何時算真的完成

宣告完成前逐條核對，任何一條答不出「證據在哪」就不算完成：

1. **每一項交付物都有本 session 的工具結果佐證**（檔案寫入成功的回傳、測試輸出、read-back 結果）。「我已經寫好了」不是證據，`Write` 工具的成功回傳才是。
2. **驗收條件逐條對過**，不是「大致都涵蓋了」。
3. **該 push 的已 push**（本環境 container 會回收，只 commit 不 push 等於沒做）。
4. **回報裡沒有未兌現的承諾**：最後一段若出現「接下來我會…」「之後可以…」而那件事屬於本次任務範圍，回去做完再收尾。
   - ✅ 正例：「已更新 8 張影片卡片（commit abc123 已 push），read-back 確認 8 個標題都在檔內，stats 列的計數已同步改為 8。」
   - ❌ 反例：「已完成儀表板更新！」——沒有 commit hash、沒有驗證證據、沒說改了哪裡。
5. **失敗也要如實收尾**：測試沒過就說沒過並附輸出；跳過的步驟明說跳過。把失敗包裝成完成是本制度最重的違規。

## §3 何時該停下來問使用者

**該問**（符合任一）：
1. 動作不可逆且超出原始請求的字面範圍（刪東西、對外發佈、改 main 分支、動金流或帳號設定）。
2. 兩種合理解讀會導向明顯不同的成品，而且做錯要重來。
   - ✅ 正例：「把儀表板改成英文版」——是新增英文版還是取代中文版？重做成本高，先問。
   - ❌ 反例：「修一下那個計數錯誤」——打開檔案就能確認哪個計數錯，不用問。
3. 真正的範圍變更：做到一半發現正確解法需要動使用者沒提過的東西（例如要動 hooks、要開新 repo）。

**不該問**（先自己做）：
- 環境裡查得到的事實（檔案內容、工具有沒有、分支叫什麼）。
- 可逆且在原始請求範圍內的實作細節。
- 「做完了要不要我做 X？」——做完先交付，追加建議放在收尾，不要用問題擋住交付。

問的方式：一次把所有要問的湊成一批，附上你的建議選項，不要擠牙膏式一題一題問。主對話通常有 `AskUserQuestion` 工具（一次最多 4 題）；若你的工具清單裡沒有它，用純文字提問並結束回合等待回覆。**subagent 不直接問使用者**——把問題寫進回報，由主對話決定要不要問。無人值守 session（排程觸發）問不到人時的處理見 `05-letter-to-future-sessions.md` §1 的 fallback 規則。

## §4 什麼訊號代表方向錯了（該換路，不是再試一次）

出現任一訊號，停止當前做法，換方法或升級或問人：

1. **同樣的錯誤換句話重試仍然出現。** 錯誤訊息內容相同＝環境在告訴你前提錯了。
   - ✅ 正例：WebFetch 某網站連兩次 403 → 換來源（如改抓 RSS、改用搜尋引擎快取），而不是第三次 WebFetch 同一網址。
   - ❌ 反例：403 之後嘗試關掉 TLS 驗證或繞過 proxy——這是禁止事項，不是換路。
2. **修好 A 弄壞 B、修好 B 又弄壞 A**：兩次以上互相打架＝你的修法在錯的抽象層，退一層看結構。
3. **為了讓方案成立，需要的假設越來越多**（「只要使用者其實是想要…就說得通」）——假設堆疊是方向錯誤的典型味道。
4. **工作量預估不斷膨脹**：原以為 5 分鐘的事做了三輪還沒完，停下來重新評估，別被沉沒成本拖著走。

## §5 品質底線怎麼驗（本 repo 適用的最低標準）

改動 `index.html` 後，收尾前至少做到：

1. **語法完整性**——只數標籤總數是不夠的（2026-07-05 實例：標籤數對稱但整份第二文件被吞進第一個 `<script>` 裡，見 LESSONS）。必查三項：
   - `grep -c '<!DOCTYPE' index.html` 必須是 1。
   - `grep -n '<script\|</script>' index.html` 的輸出必須嚴格交替：每個 `<script` 的下一筆必須是 `</script>`，不能連續兩個開標籤。`<style` 同法檢查。
   - 有 node 可用時，把每個 script 區塊內容存成暫存檔跑 `node --check` 驗語法。
2. **內容抽查**：新加的每一筆資料，用 `Grep` 逐筆確認存在於檔內（標題、連結各查一次）。
3. **一致性**：畫面上的統計數字（影片數、分類數）與實際資料筆數一致。
4. **語言**：UI 文案是繁體中文，沒有混入簡體字或不必要的英文。
5. **沒有殘留**：沒有 TODO、placeholder（「範例影片」「lorem」）、或上一版遺留的過期資料。

## §6 誠實條款：這套制度補不了什麼

拆解、驗證、多樣本評審能補「執行品質」，補不了「品味與模糊判斷」。遇到以下情況，不要假裝制度能解：

- **品味題**（視覺設計好不好看、文案哪版更順、「推薦」選片選得準不準）：產出 2–3 個候選 → 派 `fable`（不可用則 `opus`）評審選優 → 若仍不確定，把候選直接給使用者選，明說「這是品味判斷，我給出選項而非答案」。
- **模糊題**（使用者的目標本身不清楚）：不要用制度硬推進，回到 §3 問使用者。
- **查不到的事實**：標註「未能確認」，不要編造。寧可交付含明確空白的成品，不要交付含捏造內容的成品。
