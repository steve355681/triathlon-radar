# 派工 prompt 模板

> 用法：複製對應模板，填掉所有 `【…】` 空格後作為 Agent 工具的 `prompt`。空格沒填完就不要派。
> 每個模板已內建「三件套」（目標與動機、驗收條件、回報格式）與回報合約，不要刪掉這些段落。
> 模型與 agent 類型的選法見 `01-delegation.md` §1–§2；下方每個模板附預設建議，可依該表調整。

## T1 搜尋（在 codebase 裡找東西）

預設：`subagent_type: "Explore"`，`model: "haiku"`（範圍大或語意模糊時用 `sonnet`）。

```
目標：在【路徑範圍】中找出【要找的東西】。
動機：我正在【上層任務】，需要這個結果來【下一步用途】。
範圍與線索：從【起點檔案/關鍵字/命名慣例】開始查；也檢查【可能的別名或變體】。
搜索廣度：【medium / very thorough】。

驗收條件：
- 每個結果附 檔案路徑:行號。
- 明確回答「找到幾處」；一處都沒有就直說「未找到」，並列出你查過哪些地方。

回報格式：
- 條列，每條一行：路徑:行號 — 一句話說明該處是什麼。
- 不要貼超過 3 行的程式碼片段。不要建議修改方式，只回搜索結果。
```

## T2 實作（寫新功能或改行為）

預設：`subagent_type: "general-purpose"`，`model: "sonnet"`。

```
目標：在【檔案/模組】實作【功能描述】。
動機：使用者要【最終目的】；這個改動會被【誰/什麼流程】使用。
現況：【相關檔案與行號、既有慣例、要沿用的模式】。
限制：【不可動的東西，例如：不可 Write 全檔覆寫 index.html、不可改 main 分支、UI 文案必須繁體中文】。

驗收條件（逐條可檢查）：
1. 【行為 A 成立，驗法：…】
2. 【行為 B 成立，驗法：…】
3. 通過 .claude/guides/02-judgment.md §5 的品質底線檢查。

回報格式：
- 第一行：完成/部分完成/失敗。
- 改了哪些檔案：路徑:行號範圍，每個一句話說明。
- 驗收條件逐條回答通過與否，附證據（工具輸出摘要）。
- 遇到的意外與你做的取捨（沒有就寫「無」）。
- 不要貼完整檔案內容。
```

## T3 重構（不改行為的結構調整）

預設：`subagent_type: "general-purpose"`，`model: "sonnet"`；方案有取捨疑慮時先派 `opus` 評估再動手。

```
目標：把【目標範圍】從【現狀結構】重構為【目標結構】，外部行為不變。
動機：【為什麼值得重構——例如：讓之後每週更新只需改一個 JSON 區塊】。
行為不變的定義：【使用者可觀察到的哪些東西必須完全一樣，例如：頁面渲染結果、所有文案、所有連結】。

驗收條件：
1. 重構前先記錄基準：【怎麼取基準，例如：Grep 出所有影片標題與連結存成清單】。
2. 重構後同法取一次，兩份完全一致。
3. 【結構目標達成的可檢查判準，例如：資料只存在於一個 <script type="application/json"> 區塊】。
4. 通過 02-judgment.md §5 品質底線。

回報格式：
- 第一行：完成/失敗。
- 基準比對結果（一致/不一致，附差異）。
- 結構前後對照：三句話以內。
- 若中途發現行為不可能完全不變，停止並回報原因，不要硬做。
```

## T4 研究（查外部資料、網頁、文件）

預設：`subagent_type: "general-purpose"`，`model: "sonnet"`。

```
目標：查清楚【問題】。
動機：我在做【上層任務】，這個答案決定【哪個決策】。
來源建議：【起點 URL / 搜尋關鍵字 / 該用的 MCP 工具】。
時效要求：【需要多新的資訊；過時資訊是否可用】。

驗收條件：
- 每個結論附來源（URL 或 檔案:行號）。
- 區分「來源明說的」與「你推斷的」，推斷要標註。
- 查不到就回報「查不到」＋查過的來源清單；禁止編造。

回報格式：
- 先一段直接回答問題（5 句話以內）。
- 然後條列證據：結論 — 來源。
- 原文超過 30 行的部分寫到【落檔路徑，通常在 scratchpad】，回報只給路徑。
```

## T5 審查（fresh-context 驗收，包含 read-back）

預設：`subagent_type: "general-purpose"`，`model: "sonnet"`；高風險判斷用 `opus`。
**注意：prompt 裡不要透露產出者是誰、也不要透露你期望的結論。**

```
目標：獨立驗收【檔案路徑或改動範圍】是否符合下列驗收條件。
背景：這份產出的用途是【用途】。你沒有參與製作，請只依據實際檔案內容判斷。

驗收條件（逐條核對）：
1. 【條件一】
2. 【條件二】
3. 【…】

方法要求：
- 實際讀取檔案（read-back），不要依據檔名或摘要推測。
- 可執行的東西實際執行驗證；不可執行才用靜態檢查。
- 額外檢查：規則互相矛盾、路徑或工具名寫錯、會被誤讀的模糊語句。

回報格式：
- 逐條回答：通過 / 不通過 / 部分通過，各附 檔案:行號 證據。
- 最後一段：整體判定（放行 / 退回），退回時列出必須修的點（不含建議性美化）。
- 不要動手修改任何檔案。
```

## 派工後的主對話責任

- 收到回報只整合結論；要細節用 `SendMessage` 問原 agent，不重派。
- subagent 失敗時走 `01-delegation.md` §6 升降級，升級 prompt 必附完整失敗軌跡。
- 審查（T5）退回的點修完後，同一個審查 agent 用 `SendMessage` 複驗，直到放行。
